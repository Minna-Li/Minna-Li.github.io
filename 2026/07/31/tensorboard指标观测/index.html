2. actor/ppo_kl (KL 散度)

  • 含义：衡量当前训练的 Actor 模型（）与上一轮迭代的旧策略（）之间的偏离程度，防止策略更新幅度过大。
  • 理论计算公式：
  • 实际计算公式：
    $$\text{KL}{\text{batch}} = \frac{\sum{i=1}^{B} \sum_{t=1}^{T_i} \left[ \log \pi_{old}(a_{i,t}|s_{i,t}) - \log \pi_\theta(a_{i,t}|s_{i,t}) \right]}{\sum_{i=1}^{B} T_i}$$
    其中 为当前 Batch 的样本数， 为第 个样本实际生成的有效 Token 数量，分母 是当前 Batch 中所有有效 Token 的总个数。
  • 代码实现（verl/trainer/ppo/core_algos.py:1329-1333）：
    negative_approx_kl = log_prob - old_log_prob
negative_approx_kl = torch.clamp(negative_approx_kl, min=-20.0, max=20.0)
ratio = torch.exp(negative_approx_kl)
ppo_kl = verl_F.masked_mean(-negative_approx_kl, response_mask)
    其中 log_prob 是当前策略 的对数概率，old_log_prob 是旧策略 的对数概率。ppo_kl = log(π_old) - log(π_θ) 的 masked mean，即当前策略与旧策略之间的 KL 散度近似。注意这里对 negative_approx_kl 做了 [-20, 20] 的截断，防止数值溢出。

3. actor/entropy (熵)

  • 含义：衡量模型输出概率分布的离散程度与随机性。熵越高探索性越强，熵过低可能导致模型坍缩。
  • 计算公式：
  • 代码实现（verl/trainer/ppo/ray_trainer.py:1565-1572）：
    entropy_agg = agg_loss(
    loss_mat=entropys,
    loss_mask=response_masks,
    loss_agg_mode=actor_config.loss_agg_mode,
    loss_scale_factor=actor_config.loss_scale_factor,
)
    其中 entropys 来自 _compute_old_log_prob 函数，是每个 token 位置的策略熵。使用 agg_loss 聚合，DAPO 默认使用 token-mean 模式，即对所有有效 token 的熵取平均。熵的计算公式：，对整个词表的概率分布计算。

4. actor/grad_norm (梯度范数)

  • 含义：衡量当前模型参数梯度的模长，是监控梯度爆炸的核心指标。
  • 计算公式：
    $$|g|2 = \sqrt{\sum{i=1}^{n} (\nabla_{\theta_i} L)^2}$$
    是模型中所有可训练参数（Weights / Biases）的总数。
  • 代码实现（verl/workers/engine_workers.py）：
    grad_norm = self.engine.optimizer_step()
# ...
metrics["grad_norm"] = grad_norm
    在优化器步骤中计算，通常是梯度裁剪后的梯度 L2 范数。反映了反向传播时参数更新的幅度。

  • 计算公式：
    统计在一个 Batch 中，满足 的 Token 占比。

补充：

  • 上界截断与下界截断的核心区别在于新策略相比旧策略，Token 的生成概率是大幅上升还是大幅下降。触发上界截断代表模型对某些动作变得非常激进、自信。如果该值过高，说明模型容易对某些高回报 Token 产生盲目自信，可能需要降低学习率；
  • 触发下界截断代表模型正在快速遗忘、抛弃或压制某些动作。如果该值持续偏高，说明模型在频繁否定之前的行为，可能导致训练震荡或有用模式的丢失。

  • 代码实现（verl/trainer/ppo/core_algos.py:1346-1352）：

    # 标准 PPO clip 触发率
pg_clipfrac = verl_F.masked_mean(torch.gt(pg_losses2, pg_losses1).float(), response_mask)

# Dual-clip 触发率（DAPO 特有）
pg_clipfrac_lower = verl_F.masked_mean(
    torch.gt(clip_pg_losses1, pg_losses3) * (advantages < 0).float(), response_mask
)

    其中：

    • pg_losses1 = -advantages * ratio（未截断的 loss）
    • pg_losses2 = -advantages * torch.clamp(ratio, 1-cliprange_low, 1+cliprange_high)（截断后的 loss）
    • pg_losses3 = -advantages * clip_ratio_c（Dual-clip 的阈值，默认 c=3.0）
    • clip_pg_losses1 = torch.maximum(pg_losses1, pg_losses2)（标准 PPO clip 后的 loss）

    pg_clipfrac：当 pg_losses2 > pg_losses1 时，表示标准 PPO clip 被触发，即截断后的 loss 大于未截断的 loss。

    pg_clipfrac_lower：当 clip_pg_losses1 > pg_losses3 且 advantages < 0 时，Dual-clip 被触发。这个指标只在 advantages < 0（坏 response）且 ratio 过大时才会触发，用于防止梯度爆炸。这是 DAPO 算法的 Dual-clip 机制，与标准 PPO 的下界截断不同。

6. 看内存

  • actor/perf/cpu_memory_used_gb：当前 Actor 进程占用的 CPU 物理内存。
  • actor/perf/max_memory_allocated_gb：Actor 模型在 GPU 上实际分配的显存峰值。
  • actor/perf/max_memory_reserved_gb：PyTorch 显存分配器为模型预留的总显存大小。

二、critic面板下核心指标

1. critic/advantages/max

  • 含义：当前 Batch 中所有有效 Token 的优势函数最大值。
  • 计算公式：
    $$\text{Adv}{\text{max}} = \max{i,t} \left( \hat{A}_{i,t} \right)$$
    其中 代表 Batch 中的样本索引， 代表样本内的有效 Token 索引。
  • 监控意义：反映了模型中“表现极其惊艳/超出预期”的 Token 或生成片段的优势上界。若该值长期异常偏高，可能暗示奖励模型（Reward Model）存在过于激进的奖励峰值。

注意：

  • 在PPO中由于critic模型可以对逐个生成的token打分，所以优势 是细化到第 个回答样本的第 个token的
  • 而在GRPO/DAPO中的组内打分是对完整生成的回答（一整个seq）进行打分，所以与 无关。同一句子的所有 Token 共享该句的优势值，因此计算公式依旧满足。

2. critic/advantages/mean

  • 含义：当前 Batch 中所有有效 Token 优势函数的全局平均值。
  • 计算公式：
    $$\text{Adv}{\text{mean}} = \frac{1}{\sum{i=1}^{B} T_i} \sum_{i=1}^{B} \sum_{t=1}^{T_i} \hat{A}_{i,t}$$
  • 监控意义：在标准 PPO 训练中，优势函数通常会经过白化（Whitening，即减去均值并除以标准差），因此该值在理论上通常非常接近 0（如图中所示，曲线稳定在 0 附近或略有波动）。如果该值严重偏离 0，说明优势归一化步骤可能出现偏差。

3. critic/advantages/min

  • 含义：当前 Batch 中所有有效 Token 的优势函数最小值。
  • 计算公式：
    $$\text{Adv}{\text{min}} = \min{i,t} \left( \hat{A}_{i,t} \right)$$
  • 监控意义：反映了模型生成中表现最差、遭到最严重惩罚的 Token 的优势下界。

4. critic/returns/max 回报/目标值指标 (Returns)

⚠️ 重要说明：为什么 GRPO/DAPO 没有 Critic 模型，却仍然出现 critic/returns 指标？

在 verl 框架中，returns 字段在所有算法中都会被赋值，其记录逻辑在 metric_utils.py 的 compute_data_metrics 函数中是无条件执行的（不依赖 use_critic 标志）。区别在于不同算法对 returns 的计算方式不同：

算法 returns 的计算方式 代码位置
PPO（含 Critic） （GAE 优势 + 价值估计），是 Critic 模型拟合的目标值 core_algos.py:compute_gae_advantage_return
GRPO / DAPO（无 Critic） returns = advantages（两者完全相同，返回同一个张量） core_algos.py:331 → return scores, scores

因此，在 GRPO/DAPO 训练中，critic/returns 面板仍然会出现，但其数值与 critic/advantages 完全一致，并不代表 Critic 模型的拟合目标，而是框架为统一接口保留的字段。

  • 含义：当前 Batch 中所有有效 Token 的回报（Returns）最大值。
  • 计算公式：
    $$\text{Ret}{\text{max}} = \max{i,t} \left( R_{i,t} \right)$$
    其中 的含义取决于算法：
    • PPO：$R_{i,t} = \hat{A}{i,t} + V{i,t}$，是 Critic 模型需要拟合的目标值（通过 GAE 计算）。
    • GRPO/DAPO：，与优势函数完全相同（组内归一化后的 score）。
  • 监控意义：在 PPO 中代表 Critic 拟合目标的上界；在 GRPO/DAPO 中等价于 critic/advantages/max。

5. critic/returns/mean

  • 含义：当前 Batch 中所有有效 Token 回报的全局平均值。
  • 计算公式：
    $$\text{Ret}{\text{mean}} = \frac{1}{\sum{i=1}^{B} T_i} \sum_{i=1}^{B} \sum_{t=1}^{T_i} R_{i,t}$$
  • 监控意义：
    • PPO：反映 Critic 拟合目标的基准水平。随着训练进行，若该曲线稳步上升，说明模型正在学会获得更高的累积回报。
    • GRPO/DAPO：与 critic/advantages/mean 完全一致，理论上接近 0（因 advantage 经过组内归一化）。

6. critic/returns/min

  • 含义：当前 Batch 中所有有效 Token 回报的最小值。
  • 计算公式：
    $$\text{Ret}{\text{min}} = \min{i,t} \left( R_{i,t} \right)$$
  • 监控意义：在 PPO 中监控回报下限，防止出现极端负向回报导致数值不稳定；在 GRPO/DAPO 中等价于 critic/advantages/min。

7. critic/rewards/max 奖励指标 (Rewards)

奖励指标代表由奖励模型（Reward Model）或规则奖励函数（Rule-based Verifier）针对生成结果打出的原始或组合奖励值。

  • 含义：当前 Batch 中样本获得的最大奖励值。
  • 计算公式：
    $$\text{Rew}{\text{max}} = \max{i} \left( r_i \right)$$
  • 监控意义：展示模型触及的最高奖励天花板。

8. critic/rewards/mean

  • 含义：当前 Batch 中奖励值的平均水平。
  • 计算公式：
    $$\text{Rew}{\text{mean}} = \frac{1}{B} \sum{i=1}^{B} r_i$$
  • 监控意义：核心训练指标之一。如图中 critic/rewards/mean 曲线所示，随着训练步数增加，奖励均值从 0.25 稳步上升至 0.6 左右并趋于收敛，直观证明了模型正在变聪明。

9. critic/rewards/min

  • 含义：当前 Batch 中样本获得的最小奖励值。
  • 计算公式：
    $$\text{Rew}{\text{min}} = \min{i} \left( r_i \right)$$
  • 监控意义：监控模型是否产出了大量零分或严重错误的回答。

10. critic/score/max 评分区指标 (Score)

在很多大模型强化学习框架（如 verl）中，score 通常独立于奖励模型的打分，代表任务本身的外部评测得分（例如数学题的最终对错校验、格式符合度等硬性指标）。

  • 含义：当前 Batch 中外部评测得分的最大值。
  • 计算公式：
    $$\text{Score}{\text{max}} = \max{i} \left( \text{Score}_i \right)$$

11. critic/score/mean

  • 含义：当前 Batch 中外部评测得分的平均值。
  • 计算公式：
    $$\text{Score}{\text{mean}} = \frac{1}{B} \sum{i=1}^{B} \text{Score}_i$$
  • 监控意义：这是衡量模型实际业务能力（如数学准确率）的金标准。其上升趋势直接对应模型真实性能的提升。

12. critic/score/min

  • 含义：当前 Batch 中外部评测得分的最小值。
  • 计算公式：
    $$\text{Score}{\text{min}} = \min{i} \left( \text{Score}_i \right)$$
  • 监控意义：评估模型在最坏情况下的表现下限。

三、 全局序列与负载均衡面板 (global_seqlen)

在分布式强化学习集群中，由于大模型生成的文本长度呈现长尾分布，直接按样本划分会导致严重的负载倾斜。global_seqlen 面板用于监控各 GPU Rank 上的 Token 负载及其均衡调度效果。

1. 基础统计算符定义

设分布式训练集群的 GPU 总数为 ，第 个 Rank 在当前训练步（Step）中被分配并处理的有效 Token 总数为 ，则定义：

  • 全局平均 Token 数：
    $$\text{SeqLen}{\text{mean}} = \frac{1}{N{\text{rank}}} \sum_{k=1}^{N_{\text{rank}}} T_k$$
  • 全局最大 Token 数（峰值负载）：
    $$\text{SeqLen}{\text{max}} = \max{k \in {1, \dots, N_{\text{rank}}}} T_k$$

    $$\text{SeqLen}{\text{min}} = \min{k \in {1, \dots, N_{\text{rank}}}} T_k$$

2. 负载均衡调度指标

  • 平衡后最小 Token 数 (balanced_min)：
    $$\text{SeqLen}{\text{balanced_min}} = \min{k} T_k^{\text{balanced}}$$

    • 工程意义：该差值定量表征了负载倾斜程度。若该值趋近于 0，说明序列平衡调度器成功消除了分布式通信气泡（Bubble Wait）。

    $$\chi^2_{\text{token}} = \mathbb{E}{s \sim \mathcal{D}, a \sim \pi{\text{old}}[\cdot|s]} \left[ \left( \frac{\pi_\theta(a|s)}{\pi_{\text{old}}(a|s)} - 1 \right)^2 \right] \approx \frac{1}{\sum T_t} \sum_{t} \left( r_t(\theta) - 1 \right)^2$$
    其中 为似然比。

    健康预期：保持稳定低值，若震荡则需检查学习率

  • 序列级卡方散度 (chi2_seq)：
    $$\chi^2_{\text{seq}} = \mathbb{E}{y \sim \pi{\text{old}}(\cdot|x)} \left[ \left( \frac{\pi_\theta(y|x)}{\pi_{\text{old}}(y|x)} - 1 \right)^2 \right]$$

    越低越好，剧增表示策略发生剧烈更新

  • 标准 KL 散度 (kl)：
    $$\mathbb{D}{\text{KL}}(\pi{\text{old}} \parallel \pi_\theta) = \sum_{y} \pi_{\text{old}}(y|x) \log \frac{\pi_{\text{old}}(y|x)}{\pi_\theta(y|x)}$$

七、timing_per_token_ms面板

  • timing_per_token_ms/gen (Rollout 推理阶段)
    • 含义：模型在 Rollout（采样生成）阶段，生成每一个 Token 所需的平均毫秒数。
    • 计算逻辑：

该指标通常是 Inference Bound（推理受限）。如果该值过大，说明推理吞吐低，应重点检查：是否开启了 KV Cache、vLLM 的 PagedAttention 是否配置合理、GPU 显存是否因长序列产生了频繁的碎片化交换。

    • 含义：在生成完成后，计算优势函数（Advantage）与奖励（Reward）阶段，处理每一个 Token 所需的平均毫秒数。
    • 计算逻辑：

此步骤通常包含 Reward Model Inference（奖励模型推理） 和 GAE（广义优势估计） 计算。如果该值异常高，说明奖励模型推理速度慢，或者 GAE 计算逻辑未在 GPU 上实现完全并行化。如果是多轮对话，此处的时间消耗与奖励函数的复杂度呈正相关。

常见优化方向: 奖励模型量化、算子融合

  • timing_per_token_ms/update_actor (策略更新阶段)
    • 含义：Actor 模型执行反向传播（Backward）和参数更新（Optimizer Step）阶段，处理每一个 Token 所需的平均毫秒数。
    • 计算逻辑：

该指标反映了 Training Efficiency（训练效率）。影响因素包括：模型参数量（Model Size）、微批次大小（Micro-batch size）、梯度累积步数（Gradient Accumulation Steps）。如果该值极高，说明模型太大而 GPU 显存受限导致无法设置足够大的 Micro-batch，从而严重拖慢了训练迭代速度。

常见优化方向: 增大 Micro-batch, 启用 ZeRO-3/FSDP

八、timing_s面板

timing_s（Timing in Seconds）面板用于记录和剖析强化学习完整迭代周期（RL Step）中各个核心阶段所消耗的绝对墙钟时间（Wall-clock Time，单位：秒）。

在一个标准的 PPO/GRPO 训练步（Step）中，控制器（Trainer Master）驱动各个分布式 Worker 协同工作。单步总耗时 在数学上由各串行或异步流水线阶段的耗时复合构成：

1. timing_s/step (一步总耗时)

  • 含义：完成一个完整的 RL 训练迭代周期所需的总墙钟时间。
  • 代码来源：由 ray_trainer.py 中的主循环计时器包围，涵盖从 Prompt 采样分发、推理生成、奖励计算、对数概率计算、优势估计到 Actor/Critic 参数更新的整个闭环。
  • 合理趋势与诊断：在训练初期（短文本阶段），该值应保持平稳。当模型进入长思维链（Long-CoT）阶段，由于响应长度 显著增加，计算量呈超线性膨胀，timing_s/step 会出现阶跃式上升或周期性剧烈毛刺。

2. timing_s/gen (Rollout 生成耗时)

  • 含义：调用推理后端（如 vLLM 或 SGLang）执行大规模采样生成（Rollout Generation）所花费的时间。
  • 底层机制：通常占据整个 RL 训练周期的绝对大头（在许多前沿大模型 RL 架构中占 70%~90% 的时间）。
  • 合理趋势与诊断：该值的波动直接反映了生成长度的变化。如果该指标异常偏高，通常需要调整 vLLM 的 gpu_memory_utilization、增加 Tensor Parallelism (TP) 规模，或优化 PagedAttention 缓存配置。

3. timing_s/old_log_prob (旧策略对数概率计算耗时)

  • 含义：在参数更新前，利用当前批次数据在旧策略（Old Policy）下重新计算前向对数概率（）的耗时。
  • 底层机制：为满足 PPO 重要性采样（Importance Sampling）的要求，必须在每轮更新前固定旧策略的输出概率分布。
  • 合理趋势与诊断：该耗时与当前 Batch 的总 Token 数量成正比。若该值过大，往往是因为微批次大小（Micro-batch Size）设置不合理或分布式显存切分效率低下。

4. timing_s/ref (参考模型基准对数概率计算耗时)

  • 含义：冻结的参考模型（Reference Model，如初始 SFT 模型）计算原初对数概率（）的耗时。
  • 底层机制：用于计算 KL 散度惩罚项（KL Divergence Penalty），防止模型在 RL 优化过程中严重偏离原始分布。
  • 合理趋势与诊断：Reference 模型通常处于只读状态（参数不更新），其前向传播耗时应当保持高度稳定。如果与 timing_s/old_log_prob 相比耗时异常，需检查其是否与 Actor 共享显存（如 verl 的 3D-HybridEngine 机制）或独立占用显存资源。

5. timing_s/adv (优势估计耗时)

  • 含义：基于奖励值、Critic 价值估计（Value Estimates）或群组相对优势（如 GRPO 逻辑）计算优势函数 的耗时。
  • 底层机制：主要在 CPU 端或轻量张量运算中执行（计算 GAE 或群组均值标准化），属于轻量级操作。
  • 合理趋势与诊断：该值通常极小（在毫秒级或数秒内，远小于模型前向/反向传播），若该值出现显著耗时，通常是由 Ray 进程间通信（RPC Serialization）开销过大导致的。

6. timing_s/update_actor (Actor 模型参数更新耗时)

  • 含义：Actor 策略模型执行多个 PPO Epoch（或多 mini-batch 梯度累积）中前向传播、反向传播（Backward）、分布式梯度同步（FSDP / Megatron-LM AllReduce）以及优化器步进的总耗时。
  • 底层机制：这是整个训练阶段计算最密集的环节。
  • 合理趋势与诊断：在长文本（Long-CoT）阶段，由于反向传播需要存储巨大的激活值（Activation Memory），如果触发了显存重计算（Activation Checkpointing）或发生了严重的 PCIe / NVLink 通信瓶颈，该指标会急剧飙升。

7. timing_s/update_critic (Critic 模型参数更新耗时)

  • 含义：Critic 价值网络进行参数更新的耗时。
  • 合理趋势与诊断：在纯 GRPO / DAPO 等不含 Critic 网络的算法架构中，该指标为 0 或不存在；在使用 PPO 架构时，其耗时通常略小于 Actor 更新（因为 Critic 模型结构通常较轻或与 Actor 独立）。

8. timing_s/reward (奖励计算耗时)

  • 含义：调用外部奖励模型（Reward Model）或规则验证器（Rule-based Verifier / Executable Verifier）对生成结果打分的耗时。
  • 合理趋势与诊断：如果使用的是静态规则代码验证（如数学验算），该耗时极低；如果调用的是大参数量的神经奖励模型，则取决于奖励模型 Worker 的推理并发吞吐量。

9. timing_s/save_checkpoint (检查点保存耗时)

  • 含义：将模型权重、优化器状态异步或同步持久化写入分布式文件系统（DFS）或本地磁盘的耗时。
  • 合理趋势与诊断：该指标在达到保存频率（Save Frequency）的 Step 会出现突发尖刺（Spike）。如果存储带宽不足，会导致整个集群在该 Step 发生严重的同步阻塞。

在分布式大语言模型强化学习（如 verl 框架）中，验证阶段（Validation Phase）不仅通过 val-score监控模型的主任务终极表现，还通过 val-aux（Auxiliary Validation，辅助验证面板） 来全方位审视模型在不同计算预算（即不同的采样数量 ）、不同评估维度（准确率 acc 与奖励值 reward）以及不同子集策略下的行为特征。

1. 指标命名解析规则

以 val-aux/aime/acc/best@2/mean 为例，TensorBoard 中的长标签通常遵循严格的层级命名规范：

  1. val-aux：所属面板，代表辅助验证指标（非主干业务指标，主要用于过程控制、行为约束与多维度评估）。
  2. aime：验证数据集名称（例如 AIME 美国数学邀请赛数据集）。
  3. acc 或 reward：评测的目标底层指标：
    • acc（Accuracy）：二值化硬标签准确率（通过规则验证器判断最终答案是否完全正确，值为 或 ）。
    • reward：奖励得分（可能是包含过程奖励、格式合规惩罚或连续分值的综合奖励）。
  4. best@2：子采样与评估策略。其中 @8（假设总共生成 8 个回答）是基底，@2 表示通过组合子采样技术，模拟“每个 Prompt 只允许生成 2 个回答”时的策略表现，best 表示取这 2 个回答中的最优解。

3. 总结

  1. 评估计算预算的边际效用（Scaling Law Analysis）：
    通过对比 best@2、best@4、best@8，研发人员可以直观看到“增加采样次数（即推理算力投入）能带来多大的准确率提升”。如果从 best@2 到 best@8 提升微乎其微，说明模型陷入了某种确定性错误，单纯靠多次采样无法解题。
  2. 解耦绝对能力与方差稳定性：
    同时监控 acc/best@2（上限潜力）与 acc/worst@2（下限稳定性），可以准确判断模型在强化学习训练过程中是“逐渐变得稳定（上限与下限收敛靠拢）”，还是“陷入震荡（虽然偶尔能答对，但方差极高）”。
  3. 奖励与准确率的对齐监控：
    对比 acc（硬标签）和 reward（综合得分）的 best@2 曲线，可以检查奖励模型或规则惩罚项是否存在“Hack（作弊）”现象——例如奖励分值很高，但实际准确率（acc）并没有同步上升。

0. 为什么加这 8 个指标（背景与动机）

GRPO 的 advantage 是按 prompt 分组归一化的（见 verl/trainer/ppo/core_algos.py:268 compute_grpo_outcome_advantage）：

scores = token_level_rewards.sum(-1)          # 每个 response 的 outcome reward（标量）
对每个 prompt 组（同一 uid 的 n 个 response）：
    mean_g, std_g = 组内 scores 的均值、标准差
    advantage_i = (score_i - mean_g) / (std_g + eps)   # eps=1e-6
    advantage_i *= response_mask

关键推论：当一个 prompt 的 n 个 response reward 全相同（组内 std_g=0，即全 0 或全 1）时：

  • score_i - mean_g = 0，std_g = 0
  • 该 prompt 下所有 advantage = 0 → 对梯度没有任何贡献（零梯度）

如果训练到某一步（上次观测在 step~120）大量 prompt 退化成“组内全同”，有效梯度 batch 就会急剧缩水，训练随之崩塌/停滞。这就是本次想监测的核心现象。

为什么现有指标看不出：critic/rewards/mean 只是全 batch reward 的均值。mean=0.5 既可能是“一半全对、一半全错”（每题内分化，梯度正常），也可能是“每题内 8 个 response 全同、不同题之间有 0 有 1”（每题零梯度）。两种截然不同的健康度对应同一个均值，所以必须加分布形状 + 分组内方差层面的指标。

sequence_reward batch.batch["token_level_rewards"].sum(-1)（第 114 行） (num_responses,)，每个 response 的 outcome reward 标量
advantages batch.batch["advantages"]（第 116 行） (num_responses, resp_len)，GRPO 算出的 advantage
response_mask batch.batch["response_mask"].bool()（第 122 行） 同上形状，标记有效 response token
valid_adv torch.masked_select(advantages, response_mask)（第 150 行） 所有有效 token 的 advantage，展平成一维
uid batch.non_tensor_batch.get("uid", None)（第 290 行） prompt 的分组 id；同一 prompt 的 n 个 response 共享同一 uid

口径对齐：分组与 advantage 完全一致——scores = token_level_rewards.sum(-1)，按 uid 分组，包含 aborted response（advantage 计算也用全量）。因此 frac_degenerate_prompts 忠实反映“哪些 prompt 产生零梯度”，与 advantage 定义对齐，不会因为口径偏差而失真。

2. 八个指标逐个说明

2.1 reward_dist/frac_zero

  • 含义：所有 response 中，outcome reward ≈ 0 的占比（“全错 response”比例）。
  • 看什么：飙升 → 大量 response 完全拿不到分（答错/超长被罚/没生成）。
  • 计算：
    rewards = sequence_reward.detach().float().cpu()
r_max = torch.max(rewards)
frac_zero = torch.mean((rewards <= eps).float()).item()   # eps=1e-6
  • 逻辑：rewards <= 1e-6 得到布尔张量 → .float() 转 0/1 → mean 即占比。

2.2 reward_dist/frac_full

  • 含义：所有 response 中，reward ≈ 本 batch 最大值 的占比（“全对 response”比例，二值 reward 下即 ≈1 的占比）。
  • 看什么：飙升 → 大量 response 全对（reward 饱和）。
  • 计算：
    r_max = torch.max(rewards)
frac_full = torch.mean((rewards >= r_max - eps).float()).item()
  • 逻辑：用 r_max 而非写死 1.0，对非二值 reward（如带 overlong penalty 的分数）也稳健。frac_zero 和 frac_full 同时飙高 是退化崩塌的强信号（说明 reward 退化到只剩两极）。

2.3 reward_dist/std

  • 含义：全 batch per-response reward 的整体标准差。
  • 看什么：趋近 0 → 整个 batch 的 reward 塌缩到单一值（完全无信号）。
  • 计算：
    std = torch.std(rewards).item() if rewards.numel() > 1 else 0.0
  • 逻辑：单个 response 时无方差，返回 0.0；否则用总体标准差。

2.4 reward_dist/frac_degenerate_prompts ⭐核心

  • 含义：组内 n 个 response reward 全同（max-min ≤ eps）的 prompt 占比 = 零梯度 prompt 占比。
  • 看什么：这是最直接的崩塌指标——飙升意味着有效梯度 batch 在缩水。
  • 计算：
    groups = defaultdict(list)
for rew, u in zip(rewards.tolist(), list(uid)):
    groups[u].append(rew)
n_groups = len(groups)
n_degen = 0
for g_vals in groups.values():
    gt = torch.tensor(g_vals, dtype=torch.float32)
    g_max = torch.max(gt).item()
    g_min = torch.min(gt).item()
    if g_max - g_min <= eps:    # 组内 reward 全同 → 零梯度
        n_degen += 1
frac_degenerate_prompts = n_degen / n_groups
  • 逻辑：按 uid 分组（与 advantage 同源），逐组判断“组内 reward 极差是否 ≤ 1e-6”。用 max-min 而非 std==0 判定全同，更稳健（不受浮点微小抖动影响）。

2.5 reward_dist/frac_allzero_prompts

  • 含义：组内 reward 全部 ≈ 0 的 prompt 占比（“整组全错”比例，崩塌模式 A）。
  • 看什么：配合 frac_allfull_prompts 区分崩塌是“全做不出”还是“全做对没分化”。
  • 计算：
    if g_max <= eps:    # 全组 reward≈0（全错）
    n_allzero += 1
frac_allzero_prompts = n_allzero / n_groups
  • 逻辑：组内最大 reward ≤ 1e-6 → 整组都没得分。注意：全错组必然也是 degenerate 组（2.4 的子集）。

2.6 reward_dist/frac_allfull_prompts

  • 含义：组内 reward 全部 ≈ 全局 max 的 prompt 占比（“整组全对”比例，崩塌模式 B）。
  • 看什么：飙升 + frac_allzero_prompts 低 → 模型对这批题“全做对了、组内无分化” → 零梯度。
  • 计算：
    if g_min >= r_max - eps:    # 全组 reward≈max（全对）
    n_allfull += 1
frac_allfull_prompts = n_allfull / n_groups
  • 逻辑：组内最小 reward ≥ 全局 max - eps → 整组都拿满。全对组也是 degenerate 组（2.4 的子集）。r_max 复用全局最大值。

2.7 reward_dist/mean_within_group_std

  • 含义：各 prompt 组内 reward std 的均值（平均“组内分化程度”）。
  • 看什么：趋近 0 → 平均每个 prompt 内部 reward 无分化（退化）。是 2.4 的连续版补充（2.4 是占比，2.7 是程度）。
  • 计算：
    within_std_sum = 0.0
for g_vals in groups.values():
    gt = torch.tensor(g_vals, dtype=torch.float32)
    if gt.numel() > 1:
        within_std_sum += torch.std(gt).item()
mean_within_group_std = within_std_sum / n_groups
  • 逻辑：逐组算组内标准差并累加，最后除以组数。单 response 组（n=1）不计入（无方差概念），但分母仍是总组数（与 advantage 对 n=1 组设 std=1 的口径一致，避免单样本组干扰）。

2.8 reward_dist/frac_zero_advantage ⭐核心

  • 含义：有效 token 中 advantage ≈ 0 的占比 = 被浪费的梯度比例（二值 reward 下 ≈ 退化组 response 占比）。
  • 看什么：直接度量“这一步有多少比例的 token 不会贡献梯度”。飙升 = 梯度信号流失。
  • 计算：
    # valid_adv = torch.masked_select(advantages, response_mask)  # 第 150 行
frac_zero_advantage = torch.mean((valid_adv.abs() <= eps).float()).item()
  • 逻辑：valid_adv 是所有有效 response token 的 advantage（已展平）。|adv| <= 1e-6 的占比即零 advantage 比例。
  • 与 2.4 的关系：2.4 统计的是“退化 prompt 数量占比”，2.8 统计的是“零 advantage token 占比”。二值 reward 下两者数值接近（退化组内每个 token 的 advantage 都是 0）；但 2.8 更直接反映梯度损失，且对非退化组中恰好 score==mean 的中间 response 也计入（这类 token 同样无梯度）。

3. 指标之间的关系与诊断指引

                  reward 退化 → 梯度崩塌 的因果链
reward 两极化 (frac_zero↑ & frac_full↑, std↓)
         │
         ▼
组内 reward 全同 (frac_degenerate_prompts↑, mean_within_group_std↓)
         │
         ▼
advantage=0 (frac_zero_advantage↑) → 有效梯度 batch 缩水 → 训练崩塌

判读要点：

  • frac_degenerate_prompts 与 frac_zero_advantage 是两个核心指标，前者定位“哪些 prompt 零梯度”，后者度量“梯度损失比例”。
  • frac_allzero_prompts vs frac_allfull_prompts：区分崩塌是“题太难全错”还是“题太简单全对无分化”。
  • std（整体）与 mean_within_group_std（组内）一起看：整体 std 还行但组内 std 塌缩，说明“跨题有分化、题内无分化”——这正是 GRPO 失效的典型形态，critic/rewards/mean 完全看不出。
  • 全部值域 [0,1]（除 std 外），.item() 成 Python float，与现有 metrics 同格式，经 logger.log(data=metrics, step=...) → Tracking 自动进 TensorBoard。

边界 / 退化情况：

  • 无 response（rewards.numel()==0）或无 uid 时，相关指标返回 nan，不会报错。
  • 全 batch reward 恒为同一值（如全 0）时，r_max 即该值，frac_full 也会=1（“全等于最大值”），此时 frac_degenerate_prompts=1、frac_zero_advantage=1 已坐实崩塌，不会误判为健康。

4. 实现特性

  • 只读、不改训练数学：全部在 with torch.no_grad(): 下、仅 .detach() 后做统计，对训练计算零副作用。
  • 轻量：每个 step 调用一次；分组循环规模 = prompt 数（train_prompt_bsz=64 组，每组 n_resp_per_prompt=16 = 1024 response），可忽略。
  • 口径与 advantage 同源：复用 sequence_reward、valid_adv、uid，与 core_algos.compute_grpo_outcome_advantage 的分组/含 aborted 口径完全一致，保证 frac_degenerate_prompts 忠实等价于“零梯度 prompt 集合”。
